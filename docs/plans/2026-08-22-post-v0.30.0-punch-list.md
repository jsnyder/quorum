# Post-v0.30.0 punch list

Queued 2026-08-22, after the v0.30.0 fix (PR #477) and the first follow-up
(PR #478, open). Ranked by cost against the failure each prevents, per a
prioritisation review. Items explicitly dropped are recorded at the bottom so
they don't get re-litigated.

## The through-line

quorum records its own failures faithfully and never reads them back.

- `reviews.jsonl` recorded crit+high/file falling 1.17 -> 1.09 -> 0.014 across
  the 0.28.0 boundary.
- `skill_invocations.jsonl` recorded `parse_error_class: wrong_schema` 213 times.
- Every affected run still exited 0.

Three accurate ledgers, none surfaced. The outage lasted two months not because
the data was missing but because nothing read it. Prefer cheap guards that make
existing data loud over new systems that collect more of it.

## Confirmed: it was not avoidable by habit

89 reviews between 2026-06-10 and 2026-08-22:

| path | runs | crit+high/file |
|------|-----:|---------------:|
| plain `code` mode (broken axis path) | 83 | 0.122 |
| `--ensemble` (legacy fallback, working) | 5 | 0.250 |
| `--deep --ensemble` (legacy fallback, working) | 1 | 1.000 |

`resolve_axes` falls back to the working legacy reviewer for `--deep`,
`--daemon`, `--ensemble` and `--mode plan|docs`. Only default `code` mode took
the broken path -- and that was 93% of runs. Both 0.28.0 and 0.29.0 were
affected, so a stale build was no escape either. Escape-hatch sample sizes are
small (8 and 2 files); directional, not conclusive.

## KNOWNS -- do these

### 1. Version-keyed severity trend in `stats`  -- DONE (PR #478)

`reviews.jsonl` already carries `quorum_version`. Group crit+high per file
reviewed by version; warn loudly when the newest version falls below half the
trailing median. Print at the end of every review run, not behind a subcommand
nobody runs.

Why first: converts the worst failure class from invisible to same-day loud, on
a tool whose entire recent history is exactly that failure. Needs no new schema.

**Shipped:** `dimensions::group_by_version` + `detect_severity_regression`,
`stats --by-version`, and an alarm at the end of every `review`.

**Threshold tuned against real history, not intuition.** Replaying over this
project's 32 versions: ratio 0.5 fires on 8 of 32, 0.35 on 6, 0.25 on 2, and
0.20 on exactly 1 -- the version that was actually broken. 0.5 was the intuitive
value and would have trained the alarm straight into the ignore pile. Baseline
versions are held to the same 20-file minimum as the candidate; per-version
samples range 3 to 1154 files here.

**Known limitation -- crit+high/file is a proxy, not the signal.** It is
confounded by *what* was reviewed: a clean repo and a broken reviewer look
alike. The real failure was narrower and directly measurable -- the LLM leg
emitted zero findings.

**v2, and it is mostly already scaffolded:** `ReviewRecord` already declares
`skills_used`, `skill_findings: Option<HashMap<String, u32>>` and
`integrator_findings_out: Option<u32>` -- and they are DEAD. No DB columns, and
`main.rs` hardcodes them to `Vec::new()` / `None`. Populating them (the data is
in scope at the executor call sites) would let the alarm key on "axes ran and
produced nothing", which is codebase-independent and would have fired on the
very first broken run rather than needing 20 files of evidence. Sequence this
after item 3, which needs the same counters.

### 2. `missing-await` misfires (~40 FPs/run on async Python)

Fires on correctly-awaited calls, so the `skip_test_files` scoping from #478
does not help. **Fix or disable.** A rule wrong ~95% of the time has negative
value: it trains skimming, and mass-marking its output as FP writes junk labels
into the logistic calibrator.

### 3. Wire the dead axis-output counters, and distinguish "empty" from "discarded"  (~1 day)  [NOW TOP PRIORITY]

**Promoted above items 4-7.** The v0.30.0 alarm (item 1) detects *systemic*
silence from a trend and needed 146 files of evidence to be confident; it is
also confounded by what you happen to review, since a clean codebase and a dead
reviewer look alike. This detects *this run's* silence immediately, with no
statistics at all. Different guarantees, and the immediate one is worth more.

It is wiring, not design: `ReviewRecord` already declares `skills_used`,
`skill_findings: Option<HashMap<String, u32>>` and
`integrator_findings_out: Option<u32>`, all three dead -- no DB columns,
hardcoded to `None` in `main.rs` -- and the data is in scope at both
`execute_matrix` call sites.

With those populated the rule is simply: axes attempted > 0 and parseable
output == 0 is a failure, not a clean file. That covers the 174 of 440 bad
invocations the parse-failure warning misses (they reported `exit_status: ok`
with zero findings), and it would have fired on the very first broken run in
June rather than needing two months of trend.



#477 warns and floors exit at 1 when an axis *fails*. That covered 213 of the
440 bad invocations. The other 174 reported `exit_status: ok` with zero
findings, where genuinely-empty and silently-discarded are indistinguishable.
Add a counter: axes attempted vs axes producing parseable output.

### 4. Freeze the remaining recall fixtures into `eval/corpus/`  (~1 day)

The JS fixture landed in #478. Still only in transcripts:
- **YAML**: home_assistant plant packages, 4 known bugs live in HEAD, measured 1/4.
- **Python**: 208-line audio_context_capture diff, 6-item behavioural answer key,
  measured 1/6 plus 6-7 real findings the key missed.

Wrap in a pre-release script printing hits/misses per fixture. This is the
false-negative channel a solo maintainer can actually feed. Gate item 7 on it.

### 5. `classify_in_diff` over-tags  (~half day)

`src/pipeline.rs`. Anchor-based: a finding spanning 274 lines is marked in-diff
whenever its *start* line falls in a changed hunk. Its own doc comment claims it
"avoids marking wide-span findings as in-diff" -- only true when the anchor sits
outside the hunk. Replace with range intersection plus a minimum overlap.
Matters because `in_diff` feeds gating and calibration.

### 6. Verify: retry LLM call bypasses the per-review call budget  (~2h)

`skill_executor.rs`, flagged `high` by quorum reviewing its own diff. Pre-dates
v0.30.0. Cost bug, not correctness. Verify before fixing.

### 7. Minimal `fp_kind` patch

Thread `fp_kind` through `ExternalVerdictInput` and reconcile the CLI
(`trust-model`) / MCP (`trust_model_assumption`) enums. Live data corruption:
the External path silently drops the field, so calibration labels are wrong.
A day, not a refactor -- explicitly NOT the full ingestion unification.

## EXPLORE -- measure before building

### 8. Diff-aware axis prompts  (1-day EXPERIMENT, not a feature)

**Do not start before item 4 exists**, or there's no way to know if it worked.

Hypothesis: the axes receive `source.clone()` -- the whole file, undifferentiated.
`--diff-file` only scopes hydration and stamps `in_diff` afterwards, so the diff
is presentation, never input. None of the six axes is "what did this change do
to what already existed."

Evidence: measured recall is 4/4 on embedded JS (all four bugs single-site) but
1/4 on Jinja YAML (cross-template) and 1/6 on Python. Everything missed required
multi-hop reasoning about the change against existing behaviour -- a new default
colliding with a fixture, a fabricated 0.8 confidence colliding with a new
`>= 0.8` gate, a sampling gate that also gated an unrelated recovery path.
Everything hit was inspectable within one or two functions.

Test: prepend the hunks with "these lines changed; reason about how they
interact with existing behaviour." Run against all three fixtures.
- Python 1/6 -> 3/6: ship and iterate.
- No movement: a month saved, and the bottleneck is cross-file context -- a much
  more expensive project, to be deferred deliberately rather than drifted into.

**Concrete example worth citing if this gets built.** On a Shelly mJS file a
second reviewer flagged a one-line missing bounds check -- `charCodeAt(i+1)`
without the `need()` guard every neighbouring branch used. Trivial bug. But its
*severity* is only visible with runtime knowledge: an out-of-bounds read throws
inside an async BLE callback, which terminates the whole script, potentially
leaving a mains relay energised. Nothing syntactic separates that from a routine
bounds nit.

That is the sharpest form of the claim: the axis buys **severity calibration**,
not recall. The general axes already find bugs of this shape -- they rate them
medium.

Known ceiling: not sufficient on its own. Some answer-key items needed the test
suite *run* (quorum executes nothing) or evidence from another file.

### 8b. Systematic model tradeoff study  (~1 day, gated on item 4)

Today's numbers are n=1 per model on a single 187-line file. Enough to justify
the default bump to gpt-5.6, not enough to reason about tradeoffs.

Route this through `eval/run_benchmark.py` rather than ad-hoc runs, across all
frozen fixtures (JS, YAML, Python), recording per model: ground-truth hits,
total findings, LLM-sourced findings, severity distribution, tokens in/out,
wall-clock, and cost per ground-truth bug.

Candidates: gpt-5.6, gpt-5.5, gpt-5.4, gpt-5.4-mini, claude-opus-5,
claude-sonnet-5, gemini-3-pro. The mini/flash tiers matter most -- if
gpt-5.4-mini (0.75/4.50) reaches 3/4, the cost picture changes completely.

**Always export `QUORUM_BYPASS_PROXY_CACHE=1` (or pass `--no-cache`).** A cached
replay of a previous model's answers is indistinguishable from a fresh run and
already cost one session a wrong conclusion. A 1.7s review is a cache hit.

**Score axes by ground-truth attribution, not yield.** Per-axis yield since the
fix (all models, all files, from `skill_invocations.jsonl`):

| axis | runs | findings | find/run | out tok | tok/finding |
|------|-----:|---------:|---------:|--------:|------------:|
| architecture | 24 | 83 | 3.5 | 26,271 | 317 |
| correctness | 28 | 73 | 2.6 | 52,309 | 717 |
| security | 28 | 53 | 1.9 | 31,949 | 603 |
| simplicity | 28 | 52 | 1.9 | 31,514 | 606 |
| performance | 24 | 42 | 1.8 | 21,704 | 517 |
| testing-antipatterns | 28 | 12 | 0.4 | 6,785 | 565 |

Do **not** act on this table as-is; it measures productivity, not usefulness.
Two traps:

- `testing-antipatterns` looks dead at 0.4 find/run, but the JS fixture has no
  tests and it correctly returned `[]` (5 output tokens). Firing rarely on files
  with no tests is right, not lazy. Judge it only on files that HAVE tests.
- `architecture` leads on volume at a third the tokens per finding, yet
  contributed **zero** ground-truth hits on the JS fixture -- all four bugs came
  from correctness and security. Volume is not value.

The question to answer is therefore: **which axes contribute ground-truth hits,
and which contribute only volume?** That needs per-finding attribution back to a
`ground_truth.json` id, across all three fixtures -- not a yield table. If the
JS pattern holds, four of six axes cost ~60% of tokens for no ground-truth
recall, while still producing the architectural findings that corroborated a
real production outage on the Python corpus. Both facts can be true; decide with
attribution data, not aggregate counts.

Open question worth answering in the same pass: the legacy single-prompt path
(`--ensemble`, gpt-5.4) scored 3/4 for $0.048 in 25s, against the six-axis
path's 3/4 for $0.164 in 170s -- 3.4x cheaper, 7x faster, same ground-truth
recall. The axes bought 8 extra findings and the security/architecture lenses,
which produced the unique Python findings, so they are not worthless. But if
correctness alone reaches 4/4 for a fifth of the price, the six-axis macro is
the wrong default. Measure per-axis cost-effectiveness, not just per-model.

### 8c. Contextual axis selection  (~1 day, gated on 8b's attribution data)

Today every code-mode review runs all six axes on every file regardless of what
the file is. `SkillManifest` has no applicability field -- only `axis`,
`max_severity`, `capability`, `preferred_model`. So this needs a small new
mechanism, but a cheap one.

Skipping an axis saves its full prompt (~2,800 tokens on a 187-line file) rather
than trading away coverage, which makes it strictly better than dropping an axis
outright -- the axis still fires where it is useful.

Smallest version that pays, straight from tonight's data: **run
`testing-antipatterns` only where tests exist.** It scored 0.4 findings/run
overall, but that number is honest -- the JS fixture has no tests and it
correctly returned `[]`. The predicate already exists: `is_test_file_path` in
calibrate.rs, the same helper #478 used for `skip_test_files`. This is its
mirror image (fire ONLY in test paths, rather than never).

Plausible follow-ons, each to be justified by 8b attribution data rather than
intuition:
- `performance` gated on the file containing loops or async constructs
- `architecture` gated on a minimum file size -- a 50-line script has no
  architecture to critique, and architecture led on volume while contributing
  zero ground-truth hits on the JS fixture
- language-scoped axes via a manifest `applies_to` field

Design caution: this makes coverage input-dependent, so a silently-skipped axis
becomes a new way to under-report. Whatever ships must record which axes were
skipped and why, in the same telemetry as failures -- otherwise it recreates the
0.28.0 failure shape with better intentions.

### 8d. Tune what the axes ASK for  (~1-2 days, gated on 8b)

Two prompt-level levers, both aimed at the same thing: stop spending LLM
attention on work a deterministic rule does better, and stop rewarding volume.

**(a) Finding quotas push toward volume.** Every bundled axis carries a
`target_findings` quota: architecture 6, performance/simplicity/testing 8,
correctness/security 10. Telling a model roughly how many findings to produce
biases it toward reporting marginal observations to approach the number --
worst on axes whose subject matter is subjective. Architecture is the suspect:
highest volume (3.5/run), cheapest per finding (317 tok), and **zero
ground-truth hits** on the JS fixture, with a prompt enumerating five largely
aesthetic tag categories (coupling / layering / god-object / abstraction /
boundary).

**Important caveat that weakens the simple story: the quotas are not binding.**
Measured averages sit well under target -- architecture 3.5 of 6, correctness
2.6 of 10, security 1.9 of 10. Nothing is being padded up to the number. A quota
may still bias toward reporting marginal observations without being reached, so
it is worth testing, but if dropping `target_findings` leaves volume unchanged
that is the EXPECTED result, not a failed experiment.

In that case the cause is the prompt, not the quota. Architecture's five tag
categories (coupling / layering / god-object / abstraction / boundary) are
inherently judgment calls with no ground truth, and on a 187-line embedded
script there is little architecture to critique. It returned six plausible
findings and none were bugs -- an axis being asked a question the file cannot
meaningfully answer.

Test cheaply anyway: drop `target_findings` on architecture, re-run the
fixtures, compare ground-truth hits and volume. Then, regardless of outcome,
consider whether architecture should be gated by file size (see 8c) or narrowed
to the one or two tag categories that ever produce actionable findings.

**(b) Carve ast-greppable patterns out of the prompts.** Anything reliably
expressible as a syntactic pattern should be an ast-grep rule, not a bullet in
an LLM prompt. Rules are deterministic, free, instant, and cannot hallucinate a
line number. Every such bullet in a prompt spends reasoning budget on work that
a rule already does -- and, more importantly, *crowds out* the multi-hop
change-impact reasoning that only the LLM can do, which is precisely what the
measured misses were (see item 8).

So the LLM prompts should converge on: cross-function reasoning, runtime
semantics, numeric-domain reasoning, and change-impact. Not "is this function
long" -- `local-ast` already computes cyclomatic complexity.

**Caveat, learned the hard way this session:** do not convert a pattern to a
rule unless it is *reliably* expressible. `assert-in-prod-code` fired on test
files and `missing-await` misfires ~40x per run on async Python; between them
they were ~70% of raw findings on one real diff. A bad rule has negative value.
Each carve-out needs a fixture test before the corresponding prompt bullet is
deleted, or precision moves from the LLM to the rule engine and gets worse.

Sequencing: (a) is a one-line experiment and should go first; (b) is per-pattern
work and should follow 8b's attribution data, so the patterns actually worth
keeping are known before any are converted.

### 2b. Rank rules by precision AND actionability from existing feedback  (~half day)

A rule must clear two bars, not one. **Precision** = `tp/(tp+fp)`: is it right?
**Actionability** = `tp/(tp+wontfix)`: does anyone act on it? They come apart --
`wontfix` is exactly the "technically true, not doing anything about it" verdict,
and a rule that is always correct and always ignored is still noise.

`~/.quorum/feedback.jsonl` already holds 4,883 verdicts (2735 tp / 1169 fp /
608 partial / 371 wontfix). ast-grep findings title themselves `rule_id: message`,
so per-rule attribution is a regex away. Nothing has ever queried it.

First pass, rules with n>=8 labelled findings:

| rule | n | tp | fp | precision |
|------|--:|---:|---:|----------:|
| jinja-loop-variable-scoping | 8 | 0 | 8 | 0% |
| string-byte-slice-broad | 9 | 0 | 9 | 0% |
| silent-error-conversion | 11 | 0 | 9 | 0% |
| discarded-result | 10 | 1 | 9 | 10% |

Four rules that have never been right. `jinja-loop-variable-scoping` is
independently corroborated: a Home Assistant review flagged exactly those
findings as false positives, the code correctly uses `namespace()`.

Caveat: thin sample (n=8-11 each), and only four rules cleared the bar because
most feedback entries are not ast-grep findings or predate the title format.
Widen attribution before mass deletion -- but 0/8 and 0/9 are strong enough to
act on individually now.

**UPDATE 2026-08-23: the first-pass table below is invalid as evidence.** Three
of its four rules -- `jinja-loop-variable-scoping`, `string-byte-slice-broad`,
`discarded-result` -- are `judge: required`, and that contract was never
enforced (fixed same day). They were emitting completely unjudged, so their
measured precision describes *raw speculative output*, not the rule. Any
scoring must exclude findings produced before the enforcement fix, or partition
on whether a judge verdict is present.

That is a third cause, and it comes first because it invalidates the
measurement rather than changing the response:

0. **The rule never got its filter.** Marked `judge: required` but shipped
   unjudged. Precision measured on that output says nothing. Re-measure after
   enforcement before judging the rule at all.

**Do not read a high ignore rate as "delete the rule".** Beyond cause 0 it has
two more causes needing opposite responses:

1. **Generally worthless** -- wrong or unactionable for most users anywhere,
   *and* it had a fair trial (judged, or not judge-gated). Delete from the
   bundled set.
2. **Worthless in THIS context** -- a house style, a framework idiom, or
   generated/templated code whose upstream generator nobody controls (the
   classic Django + ruff case; type-annotation conventions are another). The
   rule may be excellent elsewhere. Keep it bundled; suppress it locally.

This matters because quorum is a public tool and the feedback corpus is one
user's repos. Deleting a bundled rule because it never fires usefully *here*
overfits the tool to one codebase.

**The FpKind taxonomy is already the discriminator**, and it is populated --
1169 FP entries:

| fp_kind | n | reading |
|---------|--:|---------|
| pattern_overgeneralization | 221 | matched syntactically, benign in context -> site config |
| out_of_scope | 170 | diff-scoping artifact, NOT a rule-quality signal |
| trust_model_assumption | 46 | context-dependent trust boundary |
| compensating_control | 24 | real pattern, mitigated upstream -> context |
| hallucination | 13 | genuinely broken -> fix or delete |
| untagged | 695 | -- |

So the decision rule is: **FPs concentrated in `hallucination` (and untagged
ones that turn out to be hallucination) argue for deletion. FPs concentrated in
`pattern_overgeneralization` / `compensating_control` / `trust_model_assumption`
argue for a discriminator or a local suppression, NOT deletion.** `out_of_scope`
should be excluded from rule scoring entirely -- it measures diff scoping, not
the rule.

Both mechanisms already exist and neither is being used for this:
- `.quorum/suppress.toml` in a project root (`suppress::load_project_suppressions`)
  for per-repo suppression.
- `--fp-discriminator` on a `pattern-overgeneralization` verdict, which teaches
  the distinction rather than killing the rule.

Concrete deliverable: a `stats --by-rule` view showing per rule n, precision,
actionability, and the fp_kind mix -- so the delete-vs-configure call is made
from the mix, not from the headline rate. The four 0% rules above need their
fp_kind mix checked before any of them is removed.

Do this BEFORE 8d(b) converts any prompt patterns into new rules: it establishes
the bar a rule must clear to be worth having, using evidence already on disk.
The bar is two-sided -- high precision AND generally actionable for most users,
not just correct.

### 9. Is the calibrator biased against change-impact findings?  (~half day)

Speculative, untested, cheap to check. Every calibration mechanism is monotone
toward silence (FP precedents suppress; `context_misleading` raises thresholds;
sealing is permanent `f32::INFINITY`). "Blocking IO in an async handler" is a
crisp pattern; "this new default interacts badly with an existing fixture" reads
hedged and speculative -- the shape that resembles past false positives.

If true, quorum isn't only failing to *find* this class, it may be suppressing
it when it does. Check with `--show-suppressed` against the fixtures.

### 10b. Measure fix-verification, not just recall

Every fixture scores *recall against known bugs in unchanged code*. None measures
what may be the highest-value use in an agent-assisted workflow: **verifying that
a claimed fix actually landed.**

Real case, reported from a Home Assistant session: on a third re-run, quorum
flagged that one of the author's own fixes had silently failed to apply -- the
edit matcher missed two sites and the assertions were too weak to catch it. The
finding read as "the bug you just fixed is still here".

That failure is structurally invisible to self-review: you wrote the fix, you
believe it applied, weak tests pass, and re-reading the diff shows the change
you *intended* rather than the change that happened. A reader with no memory of
intent is better placed to notice. Four review rounds on that file each caught
something real, ending at a documented tradeoff rather than an oversight.

Fixture scores measure whether planted bugs are found. This measures whether the
tool is useful in the loop people actually work in. Worth a fixture shape of its
own: a file, a claimed fix, and a fix that did not fully apply.

### 10. Re-frame what "recall" is measured against

The Python 1/6 was scored against another reviewer's output, produced under a
different brief (behavioural impact of this change). quorum's 6-7 unique
findings -- including a blocking write in an event loop that corroborated a
12-day production outage -- weren't in that key because nobody was looking for
them. Two reviewers, near-zero overlap, both sets real.

A single score is the wrong instrument. Fixture scorecards should record
*coverage per class*, not one ratio.

## DROPPED -- deliberately, do not re-litigate

- **False-negative feedback channel.** No data source. A solo maintainer
  discovers a miss only when a bug ships and bites: rare, delayed, rarely traced
  back to "quorum saw this diff and said nothing." Weeks of schema, ingestion
  and metrics for a signal arriving a few times a year. Items 1 + 3 + 4 cover
  both silence modes for ~3 days. The fixture suite *is* the FN channel.
- **Calibration module reorg** (calibrate.rs + calibrator.rs + five satellites).
  Ugly that works, read by one person who knows the layout. Revisit only if a
  bug actually hides in the sprawl.
- **`mcp/handler.rs` test coverage as a standalone project** (559 impl / 16
  tests). Add tests when next touching the file.
- **Unified feedback ingestion, grand version.** Its main justification was as a
  prerequisite for the FN channel, which is dropped. Keep only item 7.
