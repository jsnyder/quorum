# Post-v0.30.0 punch list

Queued 2026-08-22, after the v0.30.0 fix (PR #477) and the first follow-up
(PR #478, open). Ranked by cost against the failure each prevents, per a
prioritisation review. Items explicitly dropped are recorded at the bottom so
they don't get re-litigated.

## The through-line

quorum records its own failures faithfully and never reads them back.

- `reviews.jsonl` recorded crit+high/file falling 1.17 -> 1.09 -> 0.014 across
  the 0.28.0 boundary.
- `skill_invocations.jsonl` recorded `parse_error_class: wrong_schema` 213 times.
- Every affected run still exited 0.

Three accurate ledgers, none surfaced. The outage lasted two months not because
the data was missing but because nothing read it. Prefer cheap guards that make
existing data loud over new systems that collect more of it.

## Confirmed: it was not avoidable by habit

89 reviews between 2026-06-10 and 2026-08-22:

| path | runs | crit+high/file |
|------|-----:|---------------:|
| plain `code` mode (broken axis path) | 83 | 0.122 |
| `--ensemble` (legacy fallback, working) | 5 | 0.250 |
| `--deep --ensemble` (legacy fallback, working) | 1 | 1.000 |

`resolve_axes` falls back to the working legacy reviewer for `--deep`,
`--daemon`, `--ensemble` and `--mode plan|docs`. Only default `code` mode took
the broken path -- and that was 93% of runs. Both 0.28.0 and 0.29.0 were
affected, so a stale build was no escape either. Escape-hatch sample sizes are
small (8 and 2 files); directional, not conclusive.

## KNOWNS -- do these

### 1. Version-keyed severity trend in `stats`  (~1 day)  [TOP PICK]

`reviews.jsonl` already carries `quorum_version`. Group crit+high per file
reviewed by version; warn loudly when the newest version falls below half the
trailing median. Print at the end of every review run, not behind a subcommand
nobody runs.

Why first: converts the worst failure class from invisible to same-day loud, on
a tool whose entire recent history is exactly that failure. Needs no new schema.

### 2. `missing-await` misfires (~40 FPs/run on async Python)

Fires on correctly-awaited calls, so the `skip_test_files` scoping from #478
does not help. **Fix or disable.** A rule wrong ~95% of the time has negative
value: it trains skimming, and mass-marking its output as FP writes junk labels
into the logistic calibrator.

### 3. Distinguish "all axes empty" from "all axes discarded"  (~half day)

#477 warns and floors exit at 1 when an axis *fails*. That covered 213 of the
440 bad invocations. The other 174 reported `exit_status: ok` with zero
findings, where genuinely-empty and silently-discarded are indistinguishable.
Add a counter: axes attempted vs axes producing parseable output.

### 4. Freeze the remaining recall fixtures into `eval/corpus/`  (~1 day)

The JS fixture landed in #478. Still only in transcripts:
- **YAML**: home_assistant plant packages, 4 known bugs live in HEAD, measured 1/4.
- **Python**: 208-line audio_context_capture diff, 6-item behavioural answer key,
  measured 1/6 plus 6-7 real findings the key missed.

Wrap in a pre-release script printing hits/misses per fixture. This is the
false-negative channel a solo maintainer can actually feed. Gate item 7 on it.

### 5. `classify_in_diff` over-tags  (~half day)

`src/pipeline.rs`. Anchor-based: a finding spanning 274 lines is marked in-diff
whenever its *start* line falls in a changed hunk. Its own doc comment claims it
"avoids marking wide-span findings as in-diff" -- only true when the anchor sits
outside the hunk. Replace with range intersection plus a minimum overlap.
Matters because `in_diff` feeds gating and calibration.

### 6. Verify: retry LLM call bypasses the per-review call budget  (~2h)

`skill_executor.rs`, flagged `high` by quorum reviewing its own diff. Pre-dates
v0.30.0. Cost bug, not correctness. Verify before fixing.

### 7. Minimal `fp_kind` patch

Thread `fp_kind` through `ExternalVerdictInput` and reconcile the CLI
(`trust-model`) / MCP (`trust_model_assumption`) enums. Live data corruption:
the External path silently drops the field, so calibration labels are wrong.
A day, not a refactor -- explicitly NOT the full ingestion unification.

## EXPLORE -- measure before building

### 8. Diff-aware axis prompts  (1-day EXPERIMENT, not a feature)

**Do not start before item 4 exists**, or there's no way to know if it worked.

Hypothesis: the axes receive `source.clone()` -- the whole file, undifferentiated.
`--diff-file` only scopes hydration and stamps `in_diff` afterwards, so the diff
is presentation, never input. None of the six axes is "what did this change do
to what already existed."

Evidence: measured recall is 4/4 on embedded JS (all four bugs single-site) but
1/4 on Jinja YAML (cross-template) and 1/6 on Python. Everything missed required
multi-hop reasoning about the change against existing behaviour -- a new default
colliding with a fixture, a fabricated 0.8 confidence colliding with a new
`>= 0.8` gate, a sampling gate that also gated an unrelated recovery path.
Everything hit was inspectable within one or two functions.

Test: prepend the hunks with "these lines changed; reason about how they
interact with existing behaviour." Run against all three fixtures.
- Python 1/6 -> 3/6: ship and iterate.
- No movement: a month saved, and the bottleneck is cross-file context -- a much
  more expensive project, to be deferred deliberately rather than drifted into.

Known ceiling: not sufficient on its own. Some answer-key items needed the test
suite *run* (quorum executes nothing) or evidence from another file.

### 9. Is the calibrator biased against change-impact findings?  (~half day)

Speculative, untested, cheap to check. Every calibration mechanism is monotone
toward silence (FP precedents suppress; `context_misleading` raises thresholds;
sealing is permanent `f32::INFINITY`). "Blocking IO in an async handler" is a
crisp pattern; "this new default interacts badly with an existing fixture" reads
hedged and speculative -- the shape that resembles past false positives.

If true, quorum isn't only failing to *find* this class, it may be suppressing
it when it does. Check with `--show-suppressed` against the fixtures.

### 10. Re-frame what "recall" is measured against

The Python 1/6 was scored against another reviewer's output, produced under a
different brief (behavioural impact of this change). quorum's 6-7 unique
findings -- including a blocking write in an event loop that corroborated a
12-day production outage -- weren't in that key because nobody was looking for
them. Two reviewers, near-zero overlap, both sets real.

A single score is the wrong instrument. Fixture scorecards should record
*coverage per class*, not one ratio.

## DROPPED -- deliberately, do not re-litigate

- **False-negative feedback channel.** No data source. A solo maintainer
  discovers a miss only when a bug ships and bites: rare, delayed, rarely traced
  back to "quorum saw this diff and said nothing." Weeks of schema, ingestion
  and metrics for a signal arriving a few times a year. Items 1 + 3 + 4 cover
  both silence modes for ~3 days. The fixture suite *is* the FN channel.
- **Calibration module reorg** (calibrate.rs + calibrator.rs + five satellites).
  Ugly that works, read by one person who knows the layout. Revisit only if a
  bug actually hides in the sprawl.
- **`mcp/handler.rs` test coverage as a standalone project** (559 impl / 16
  tests). Add tests when next touching the file.
- **Unified feedback ingestion, grand version.** Its main justification was as a
  prerequisite for the FN channel, which is dropped. Keep only item 7.
